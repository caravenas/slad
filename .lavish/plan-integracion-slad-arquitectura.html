Arquitectura objetivo

SLAD como executor confiable,
no como cerebro duplicado.

Pi razona y dirige. Herdr mantiene visibles las sesiones interactivas. SLAD valida y ejecuta un plan aprobado. Hooks deterministas aplican invariantes. Git, CI y un reviewer independiente deciden si el resultado se integra.

Prerequisito: resolver primero los cambios staged de slad doctor y el plan untracked. No iniciar esta migración sobre el working tree actual.

Nuevo camino feliz

  1. Pi crea un plan canónico una sola vez.
  2. slad pipeline plan --import plan.json --check.
  3. Chris/Pi aprueba el hash.
  4. SLAD ejecuta sobre una integration branch, sin aplicar todavía al main.
  5. Hooks validan cada tarea y el resultado integrado.
  6. Reviewer independiente inspecciona base..integration.
  7. Follow-ups continúan sobre la misma integration branch.
  8. slad pipeline apply hace un único squash staged.

Fase 0 · Hardening

Hacer confiables las invariantes existentes

Corregir porcelain, sesiones, manifest binding, preflight y dirty-tree policy. Añadir regresiones E2E antes de volver a usar strict ownership por defecto.

Áreas: worktrees.ts, run-parallel.ts, session.ts, persistence, shared schemas y tests.

Gate: 3 runs controlados consecutivos con strict ownership, sin falsos positivos ni intent stale.
Fase 1 · Plan externo

Separar razonamiento de ejecución

Añadir import/check de un plan canónico producido por Pi. Mantener el pipeline LLM actual como compatibilidad, pero no como ruta recomendada.

Gate: el mismo plan importado produce hash estable, preflight reproducible y no invoca LLM antes del run.

Fase 2 · Review before apply

Mantener integration branch hasta aceptar el resultado

Agregar estados running → review_pending → applied|aborted. Los follow-ups parten de integration tip. El main recibe un único squash staged al final.

Gate: un follow-up puede modificar el resultado sin commits en main, sin replanificar desde HEAD y sin doble squash.

Fase 3 · Integración global

Skill, hooks y reviewer Herdr

Actualizar el skill global con routing y comandos. Añadir hooks tipados en SLAD. Usar Herdr solo para planning/review interactivo y preservar la frontera global/proyecto.

Gate: Pi puede ejecutar el workflow completo sin duplicar stages y el reviewer recibe únicamente plan, diff, criterios y comandos.

Fase 4 · Adopción

Dogfood con métricas y rollback

Ejecutar 5 pilotos: 2 medianos, 2 paralelos y 1 interrupción/resume. Medir tiempo, regeneraciones, falsos positivos, violaciones reales y porcentaje de runs que requieren bypass.

Gate: 0 bypasses, 0 falsos positivos críticos, recovery probado y overhead aceptable frente a Pi directo.

No objetivos

  • No reemplazar Pi como capitán.
  • No mover Herdr dentro del repositorio SLAD.
  • No eliminar el pipeline legacy en la primera migración.
  • No crear un framework general de agentes o providers HTTP.
  • No implementar un DSL de hooks arbitrario antes de demostrar necesidad.

Riesgos

  • El lifecycle review/apply aumenta estados persistidos.
  • Un plan externo puede divergir del contrato si no hay una única schema.
  • Hooks arbitrarios pueden introducir riesgo; empezar con hooks internos tipados.
  • La compatibilidad legacy puede prolongar duplicación; definir métricas de deprecación.
